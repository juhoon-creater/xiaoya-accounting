# 小芽记账第一版数据库设计

状态：根据第一版规格和现有 uni-app 主页面核对后的设计草案，供实现前评审。本文定义业务数据模型，不代表数据库表已创建。

## 1. 数据库边界

开发阶段使用同一个 MySQL Server 实例，按服务划分数据库：

| 服务 | 数据库 | 负责的数据 |
|---|---|---|
| `xiaoya-user-service` | `xiaoya_user` | 用户账号和认证相关数据 |
| `xiaoya-accounting-service` | `xiaoya_accounting` | 分类、账单、预算 |

账单服务只保存 `user_id`，不跨数据库建立到用户表的外键。认证后由可信任的服务端身份上下文提供当前用户 ID，所有账单、预算查询和写入都必须带当前用户 ID 条件。

建议字符集为 `utf8mb4`，排序规则为 `utf8mb4_0900_ai_ci`。金额使用 `DECIMAL`，禁止使用浮点类型保存金额；时间统一按 `DATETIME(3)` 存储，应用和接口统一使用 ISO-8601 日期/时间格式。

## 2. 用户数据库：`xiaoya_user`

### 2.1 `users` 用户表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | 主键，自增 | 用户 ID |
| `username` | `VARCHAR(50)` | 非空，唯一 | 登录用户名；首版约定去除首尾空格，大小写不敏感 |
| `password_hash` | `VARCHAR(255)` | 非空 | BCrypt 哈希，不保存明文密码 |
| `created_at` | `DATETIME(3)` | 非空 | 创建时间 |
| `updated_at` | `DATETIME(3)` | 非空 | 最近更新时间 |

用户名唯一索引：`uk_users_username (username)`。注册时在应用层做格式校验，数据库唯一约束作为并发情况下的最终保障。

## 3. 记账数据库：`xiaoya_accounting`

### 3.1 `categories` 分类表

分类由系统维护，第一版不开放用户自定义。系统默认分类以初始化数据写入此表。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | 主键，自增 | 分类 ID |
| `name` | `VARCHAR(40)` | 非空 | 分类显示名称 |
| `type` | `VARCHAR(16)` | 非空 | `EXPENSE` 支出或 `INCOME` 收入 |
| `sort_order` | `INT` | 非空，默认 0 | 显示顺序 |
| `active` | `BOOLEAN` | 非空，默认 true | 是否启用 |
| `created_at` | `DATETIME(3)` | 非空 | 创建时间 |
| `updated_at` | `DATETIME(3)` | 非空 | 最近更新时间 |

唯一索引：`uk_categories_type_name (type, name)`。默认支出分类：餐饮、交通、购物、娱乐、学习、医疗、住房、其他；默认收入分类：工资、奖金、兼职、报销、其他。

### 3.2 `bills` 账单表

主 App 记账表单提供“支出 / 收入”切换，且切换后分类选项不同。因此收支类型是每笔账单的必填字段，不是由金额正负推断。字段明确命名为 `transaction_type`；它与分类是两个不同概念。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | 主键，自增 | 账单 ID |
| `user_id` | `BIGINT` | 非空，索引 | 所属用户 ID；不跨库设外键 |
| `category_id` | `BIGINT` | 非空，索引 | 分类 ID |
| `transaction_type` | `VARCHAR(16)` | 非空 | 用户选择的收支类型：`EXPENSE` 支出或 `INCOME` 收入 |
| `amount` | `DECIMAL(12,2)` | 非空，必须大于 0 | 账单金额 |
| `transaction_date` | `DATE` | 非空，索引 | 实际记账日期 |
| `remark` | `VARCHAR(500)` | 可空 | 备注 |
| `mood` | `VARCHAR(20)` | 可空 | Demo 记账时选择的心情标签；为空表示未选择 |
| `created_at` | `DATETIME(3)` | 非空 | 创建时间 |
| `updated_at` | `DATETIME(3)` | 非空 | 最近更新时间 |

索引建议：`idx_bills_user_date (user_id, transaction_date, id)`、`idx_bills_user_type_date (user_id, transaction_type, transaction_date)`、`idx_bills_user_category_date (user_id, category_id, transaction_date)`。列表默认按 `transaction_date DESC, id DESC` 排序。业务校验要求 `transaction_type` 与分类类型一致。

删除采用物理删除（第一版暂定）；账单详情、修改、删除必须同时匹配 `id` 和当前 `user_id`，避免跨用户访问。

### 3.3 `monthly_budgets` 月预算主表

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | 主键，自增 | 预算 ID |
| `user_id` | `BIGINT` | 非空 | 所属用户 ID |
| `budget_month` | `DATE` | 非空 | 该月第一天，例如 `2026-10-01` |
| `total_amount` | `DECIMAL(12,2)` | 非空，默认 0 | 主 App 中所有分类预算金额之和；修改分类预算时由服务端同步计算 |
| `created_at` | `DATETIME(3)` | 非空 | 创建时间 |
| `updated_at` | `DATETIME(3)` | 非空 | 最近更新时间 |

唯一索引：`uk_monthly_budgets_user_month (user_id, budget_month)`。

### 3.4 `category_budgets` 月分类预算明细表

关系为 `monthly_budgets (1) -> category_budgets (N)`：一个用户某月的预算主记录下面有多条分类额度。Demo 主 App 的操作是编辑分类预算，合计自动同步为总预算。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | `BIGINT` | 主键，自增 | 预算 ID |
| `monthly_budget_id` | `BIGINT` | 非空，外键 | 所属月预算主记录 |
| `category_id` | `BIGINT` | 非空 | 支出分类 ID |
| `amount` | `DECIMAL(12,2)` | 非空，必须大于 0 | 该分类预算金额 |
| `created_at` | `DATETIME(3)` | 非空 | 创建时间 |
| `updated_at` | `DATETIME(3)` | 非空 | 最近更新时间 |

唯一索引：`uk_category_budgets_monthly_budget_category (monthly_budget_id, category_id)`。第一版只允许对支出分类设置预算。

## 4. 初始分类数据

初始化数据应以数据库迁移脚本写入，不要求开发者手工逐条录入。脚本应可重复部署且不产生重复分类。支出/收入分类名称与顺序以本设计中的列表为准。

## 5. 迁移和约束

- DDL 与初始数据通过版本化迁移脚本管理；已执行的迁移脚本不应原地修改，结构变化新增后续版本。
- 推荐 Flyway 目录：每个服务自己的 `src/main/resources/db/migration/`。
- 迁移脚本由负责该数据的服务拥有：用户表归用户服务，其他四张表及分类初始数据归账单服务。
- 生产环境部署前需要备份策略、迁移回滚/前向修复方案和非 root 最小权限数据库账号；开发阶段不使用 root 凭证提交到 Git。

## 6. 待评审的暂定决策

1. 用户名按大小写不敏感处理，长度 3-50，允许的字符规则需在接口校验中明确。
2. 密码首版长度建议 8-72 个字符；BCrypt 有输入长度限制，服务端必须一致校验。
3. 账单删除先采用物理删除；若需要恢复或审计，再改为软删除并新增字段。
4. `budget_month` 使用该月第一天，接口对外仍使用 `YYYY-MM`。
5. 分类作为全局系统数据维护，不按用户复制一份。
